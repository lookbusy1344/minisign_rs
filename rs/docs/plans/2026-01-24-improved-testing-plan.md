# Improved Testing Plan for Minisign Rust Implementation

**Date:** 2026-01-24
**Status:** Proposed
**Related:** [2026-01-24-fix-encrypted-key-compatibility.md](./2026-01-24-fix-encrypted-key-compatibility.md)

## Executive Summary

The encrypted key compatibility bug (64-byte vs 72-byte KDF output) went undetected because:

1. **No cross-binary encrypted key tests** - All existing cross-binary tests use `-W` (no password)
2. **Slow tests are not run in CI** - The `--ignored` tests that use C-generated fixtures are never executed
3. **No fixture-based fast tests** - Tests that could catch the bug require expensive scrypt operations
4. **No test coverage requirements** - Code paths for encrypted keys lack adequate coverage

This plan addresses these gaps systematically.

### 1.2 Fix Ignored Test Situation

**Problem:** Tests marked with `#[ignore]` are never run in CI.

**Current State:**
- CI runs only `cargo test --verbose` (skips `--ignored` tests)
- Slow scrypt tests (real parameters) are never validated
- C fixture tests are effectively dead code

**Solution:** Add a separate CI job for slow/ignored tests.

```yaml
# .github/workflows/rust.yml - ADD NEW JOB

  slow-tests:
    name: Slow Tests (C Compatibility)
    runs-on: ubuntu-latest
    needs: build-and-test  # Only run after fast tests pass

    defaults:
      run:
        working-directory: rs

    steps:
    - uses: actions/checkout@v4

    - name: Setup Rust
      uses: dtolnay/rust-toolchain@stable

    - name: Install C minisign
      run: |
        sudo apt-get update
        sudo apt-get install -y minisign

    - name: Run slow/ignored tests
      run: cargo test --verbose -- --ignored
      timeout-minutes: 30

    - name: Run cross-binary tests
      run: cargo test --test cross_binary_test --verbose
      timeout-minutes: 10
```

**Priority:** 🔴 Critical
**Effort:** 1-2 hours

## 4. Documentation - Maintaining Test Quality

### 4.1 Test Writing Guidelines

Create `rs/docs/TESTING.md`:

```markdown
# Testing Guidelines for Minisign Rust

## Test Categories

### Unit Tests (inline in `src/*.rs`)
- Test single functions in isolation
- Mock external dependencies
- Must run in < 1 second
- No filesystem or network access

### Integration Tests (`tests/integration/`)
- Test multiple components together
- May use tempfiles
- Must run in < 5 seconds each
- No external binaries required

### Compatibility Tests (`tests/compatibility/`)
- Verify behavior matches C minisign
- Use pre-generated fixtures
- Must run in < 1 second each (fast path)
- Some may be marked `#[ignore]` for slow operations

### Cross-Binary Tests (`tests/compatibility/cross_binary_test.rs`)
- Execute both Rust and C binaries
- Require C minisign installed
- Run in slow-tests CI job
- Use `require_c_minisign!()` macro

## Writing New Tests

### Naming Convention
```rust
#[test]
fn test_{operation}_{variant}_{expected_outcome}() {
    // test_sign_encrypted_key_success
    // test_decrypt_wrong_password_fails
    // test_verify_tampered_message_fails
}
```

### Testing Encrypted Keys

**DO NOT** use real scrypt parameters in regular tests:
```rust
// ❌ BAD - Takes 15-30 seconds
let key = SeckeyStruct::new_encrypted(..., 20, 8, 1)?; // Production params

// ✅ GOOD - Use fast parameters for logic tests
let key = SeckeyStruct::new_encrypted(..., 14, 8, 1)?; // Fast test params

// ✅ GOOD - Use pre-generated fixtures for compatibility tests
let key_bytes = include_bytes!("../fixtures/keys/c_encrypted_password123.key");
```

### Cross-Binary Tests

Always use the `require_c_minisign!()` macro:
```rust
#[test]
fn test_cross_something() {
    require_c_minisign!();  // Skips test if C minisign not found
    
    // Test logic...
}
```

### Testing Password Input

For CLI tests requiring password input, use environment variable or file:
```rust
// Option 1: Password file (preferred for C minisign)
fs::write(&password_file, "mypassword\n")?;
Command::new("minisign")
    .stdin(fs::File::open(&password_file)?)
    // ...

// Option 2: Echo pipe
Command::new("sh")
    .args(["-c", "echo 'password' | minisign -S ..."])
    // ...
```

### 4.3 When to Use Fast vs Slow Tests

Add to `rs/docs/TESTING.md`:

```markdown
## Fast vs Slow Tests

### Fast Tests (default `cargo test`)

Use when testing:
- Logic correctness (encryption XOR, checksum calculation)
- Error handling paths
- Serialization/deserialization
- CLI argument parsing

Fast test parameters for scrypt:
```rust
const FAST_LOG_N: u8 = 14;  // 2^14 = 16384 (vs 2^20 = 1M for production)
const FAST_R: u32 = 8;
const FAST_P: u32 = 1;
```

### Slow Tests (`cargo test -- --ignored`)

Use when testing:
- Compatibility with C minisign using real parameters
- Performance characteristics
- Production parameter validation

Mark slow tests with `#[ignore]`:
```rust
#[test]
#[ignore]  // Slow: uses production scrypt parameters
fn test_decrypt_c_generated_encrypted_key() {
    // Uses real KDF parameters, takes 15-30 seconds
}
```

### When to Add Slow Tests

Add a slow test when:
1. Testing byte-level compatibility with C implementation
2. Validating production parameter handling
3. The behavior differs between fast and production parameters

### Running Slow Tests

```bash
# Run all slow tests
cargo test -- --ignored

# Run specific slow test
cargo test test_decrypt_c_generated_encrypted_key -- --ignored

# Run all tests including slow ones
cargo test -- --include-ignored

## Appendix B: Why This Bug Was Missed

### Root Cause Analysis

1. **Test Isolation:** Rust tests encrypt and decrypt with their own (incorrect) implementation—both use 64 bytes, so they "pass"

2. **Fixture Gap:** C-generated encrypted key fixture existed (`test.key`) but the test was `#[ignore]`d and never run in CI

3. **Cross-Binary Gap:** All cross-binary tests used `-W` (unencrypted) for speed, missing the encrypted key code path

4. **Coverage Blindness:** No coverage tracking meant no visibility into untested encrypted key paths

### Lessons Learned

1. **Cross-implementation tests are critical** - Self-tests can't catch protocol mismatches
2. **Ignored tests are invisible** - They must run somewhere, or remove them
3. **Fixtures should cover all variants** - Unencrypted AND encrypted
4. **CI should validate what production uses** - If production uses encrypted keys, CI must test them
